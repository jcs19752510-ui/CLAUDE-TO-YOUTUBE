# 🎁 무료 자료 ① — 클로드 규칙 파일(`CLAUDE.MD`) 템플릿

> 클로드에게 주는 **신입사원 업무 지침서**입니다. 프로젝트 폴더 맨 위에 `CLAUDE.MD`라는 이름으로 저장하면, 클로드 코드가 일을 시작할 때 제일 먼저 읽습니다.
> 아래 **복사 시작 ~ 복사 끝** 사이를 통째로 복사해 붙여넣고, `〈 〉` 칸만 본인 내용으로 바꾸세요.

## 사용법 (3분)

1. 프로젝트 폴더를 엽니다.
2. `CLAUDE.MD` 파일을 새로 만듭니다(이름은 영문 대문자 CLAUDE, 확장자 `.MD` 또는 `.md`).
3. 아래 템플릿을 붙여넣고 `〈 〉`를 채웁니다.
4. 클로드 코드를 다시 시작하면 적용됩니다.
5. 클로드가 마음에 안 드는 행동을 하면, 그 행동을 막는 **한 줄을 추가**합니다. (이게 핵심입니다.)

> 이 템플릿은 실제 24일 프로젝트(STOCK-ANALYZER-KR)의 `CLAUDE.MD` 상시 규칙을 **범용으로 다듬은 것**입니다. 그 프로젝트의 규칙 원문은 다릅니다.

---

## ▼ 복사 시작 ▼

```markdown
# 〈프로젝트 이름〉 — 작업 규칙

## 프로젝트 한 줄 소개
〈무엇을 만드는지 한 줄. 예: 한국 주식 데이터를 보여주는 개인용 웹 서비스〉

## 최상위 목표
〈이 프로젝트에서 가장 중요한 것 한 가지. 예: 데이터가 정확하고, 지연되면 지연됐다고 화면에 표시한다〉

## 상시 규칙 (모든 작업에 예외 없이 적용)

1. **내가 할 수 있는 시험은 내가 직접 한다.**
   실행·검증할 수 있는 것은 사용자에게 시키지 않고 끝까지 직접 돌려 확인한다.
   "당신의 PC에서 실행해 보세요"를 해결책으로 내놓지 않는다. 도구가 없으면 설치해서라도 직접 시험한다.

2. **사용자에게 요청하는 것은 내가 물리적으로 할 수 없는 것만.**
   (사용자 화면, 사용자 계정·비밀번호가 필요한 것, 사용자만 내릴 수 있는 결정)
   요청할 때는 ① 무엇이 막혔는지 ② 왜 내가 못 하는지를 먼저 말한다.
   시키는 일은 **한 번에 한 가지**만, 이유와 함께. 같은 일을 두 번 시키지 않는다.

3. **모든 작업에는 시험 결과서를 쓴다.** 위치: `〈docs/qa/〉`
   범위 · 환경 · 변경 요약 · 시험 항목(기대값/실제값/결과) · 발견한 문제 · 고친 것 · **확인하지 못한 것과 위험**.
   확인하지 못한 것은 숨기지 않고 정직하게 적는다. 해결된 척하지 않는다.

4. **모르면 묻고, 마음대로 결정하지 않는다.**
   단, 아주 특이한 것만 묻고 나머지는 합리적으로 진행한다. 되돌리기 어려운 결정은 반드시 먼저 묻는다.

5. **고치기 전에 재현 시험부터 쓴다.**
   버그를 고칠 때는 먼저 같은 문제를 일으키는 시험을 만든다. 옛 코드에서는 실패하고, 고친 코드에서는 통과해야 한다.

6. **완료 전 체크리스트를 모두 통과한 뒤에만 "끝났다"고 말한다.**
   〈본인 프로젝트에 맞게. 예: 린트 / 전체 시험 / 빌드 / 화면 확인 / 결과서 작성 / 결정 기록 갱신〉

7. **결정은 기록한다.** 위치: `〈docs/decisions.md〉`
   날짜 · 무엇을 · 왜 · 대안은 무엇이었나. 나중에 "왜 이렇게 했지?"에 답할 수 있어야 한다.

8. **비밀값(API 키, 비밀번호, 토큰)은 코드·로그·화면·문서에 절대 쓰지 않는다.**
   `.env` 파일은 읽기만 하고 내용을 출력하지 않는다.

## 위험한 일은 반드시 사용자 승인 후에만

- 〈실제 서버 배포〉
- 〈데이터 삭제·덮어쓰기〉
- 〈돈이 드는 서비스 가입·결제〉
- 〈외부로 데이터를 보내는 작업〉

## 작업이 끝날 때마다

1. 변경 내용을 짧게 요약한다 (한 화면 안에).
2. `git commit` 후 `〈작업 브랜치 이름〉`에 push 한다.
3. 사용자에게 남은 일이 있다면 **목록으로 정직하게** 적는다.

## 말하는 방식

- 짧고 결과 중심으로 답한다.
- 모르는 것은 추측으로 늘어놓지 않고, 확인한 것만 말한다.
- 용어는 쉬운 말로 한 줄 풀이를 덧붙인다. 〈왕초보라면 이 줄 유지〉

## 금지 사항 (내 프로젝트 전용)

- 〈예: 종목 추천·투자 권유 표현을 화면에 쓰지 않는다〉
- 〈예: 사용자 승인 없이 패키지를 새로 설치하지 않는다〉
- 〈나만의 금지 사항을 계속 추가〉
```

## 줄별 해설 — "왜 이 줄이 필요한가?" (왕초보용)

| 규칙 | 없으면 생기는 일 | 있으면 달라지는 일 |
|---|---|---|
| 1. 내가 직접 시험 | 클로드가 "실행해 보세요"라며 나에게 떠넘김 | 클로드가 직접 돌려 보고 결과만 보고 |
| 2. 요청은 최소·한 번에 하나 | 한꺼번에 열 가지를 시키고 이유도 없음 | 꼭 필요한 한 가지만, 이유와 함께 |
| 3. 시험 결과서 | "잘 됩니다"라고만 말하고 확인 못 한 건 숨김 | 확인 못 한 것까지 목록으로 정직하게 |
| 4. 모르면 묻기 | 마음대로 판단해 엉뚱한 방향으로 진행 | 중요한 갈림길에서만 질문 |
| 5. 재현 시험 먼저 | 고쳤다고 하는데 진짜 고쳐졌는지 모름 | "옛 코드 실패 → 새 코드 통과"로 증명 |
| 6. 완료 전 체크 | 대충 끝내고 나중에 터짐 | 정해진 점검을 통과해야 "끝" |
| 7. 결정 기록 | 한 달 뒤 "왜 이렇게 했지?" 아무도 모름 | 이유가 문서로 남음 |
| 8. 비밀값 금지 | API 키가 코드·화면에 노출될 위험 | 키 유출 사고 예방 |

## 자주 하는 질문

**Q. 규칙이 너무 많으면 클로드가 헷갈리지 않나요?**
A. 처음엔 1~3번만 쓰셔도 됩니다. 마음에 안 드는 행동이 생길 때마다 한 줄씩 추가하세요. 규칙은 **불편함에서 태어나는 것**이 가장 좋습니다.

**Q. 한 번 쓰면 계속 적용되나요?**
A. 클로드 코드는 시작할 때마다 이 파일을 읽습니다. 다만 지시가 너무 길어지면 일부가 덜 지켜질 수 있으니, 핵심 규칙은 위쪽에 두세요.

**Q. 규칙을 어기면요?**
A. "규칙 3번을 어겼어. 다시 해"처럼 **번호로 짚어** 주세요. 번호가 붙어 있으면 고치기 쉽습니다.
